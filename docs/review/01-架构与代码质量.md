## 一、总体评分

### **5.4 / 10**

| 维度 | 得分 | 权重 | 说明 |
|---|---|---|---|
| 分层与模块边界 | 4.0 | 20% | 层次是有的（models → agents → preactor → writer → cli/webui），但 `agents.py` 一个文件同时装 LLM Provider 适配层和 5 个业务 Agent；`utils.py` 五合一；`writer.py` 装了三类不相关职责。 |
| 正确性 | 4.5 | 25% | 存在 **12 处确凿缺陷**：共享 config 并发写竞争、token 预算漏算 3~5 倍、FastAPI 路由遮蔽、YAML 路径读不到 provider 环境变量、书名 fallback 插值出函数 repr、EPUB ID 不确定等。 |
| 可测试性 | 2.0 | 15% | **零测试**；全局单例（`logger` / `_WRITING_STYLES` / `runs`）不可注入；`LLMClient` 直接 `import anthropic/openai` 并在方法内构造，无注入点。 |
| 命名与一致性 | 3.5 | 10% | 品牌是「选墨集 / Sifted-Ink」，包名却是 `novel_preactor`、模块 `novel_preactor.novel_preactor`、logger 名 `"narrative_prism"`（NARRATIVE_PRISM 遗留）；`preactor.py` / `run_pre_actor` / `PreActorResult` 与文档口径的「预演 pre-rehearsal」全不一致。 |
| 文档与实现一致性 | 3.0 | 10% | README 声称 MOBI/AZW3 导出、`ANTHROPIC_API_KEY` 可用、「章节标题也适用」、「1~500 条情节线在分支点做出不同选择」——**这四条均未实现**（详见 D16、B15、§五）。 |
| 健壮性与错误处理 | 5.0 | 10% | 异常被吞 12 处（多为「不该让辅助功能拖垮主流程」，意图正确但无日志）；`extract_json` 的 LLM JSON 修复层写得相当扎实，是全项目质量最高的一段。 |
| 领域模型设计 | 6.5 | 10% | `StoryConfig` / `StoryState` / `Chapter` / `AgentAction` / `EvalResult` 建模清晰，dataclass 用得恰当，是全项目最好的一块。 |

**评分理由（展开）**

+ **加分项**：领域模型（`models.py`）干净；`utils.py:113-341` 的 LLM JSON 容错解析（`_repair_json` / `_fix_unescaped_quotes` / `extract_json` 五级策略）质量相当高，能真正解决实际问题；`naming.py` 的规则化候选生成 + LLM 择优两段式是好设计；`PROVIDER_REGISTRY` 的统一抽象（`agents.py:38`）确实把 13 家 provider 收敛到了一个 `LLMClient` 接口下，扩展性没问题；`webui` 的 SSE 进度流 + root logger 转 SSE 的思路是对的。
+ **扣分项**：**并发正确性有硬伤**——`preactor.py:122` 让 N 个并发版本共同写同一个 `config` 对象；**成本控制形同虚设**——`preactor.py:451` 的 token 估算只算 `write_tokens + 500`，漏掉每章 4~5 次 Agent 调用；**文档承诺系统性高于实现**（MOBI/AZW3、分支选择、per-provider env、章节标题命名全部缺失）；**零测试 + 全局单例 + 函数内 import** 组合让任何回归都必须靠真跑 API 才能发现；**34 处死代码/死字段/死方法**（约 600 行，占 9%）说明重构中途的收敛没做完。

**一句话结论**：**这不是一个「写得烂」的项目，这是一个「跑得起来但账算不清、承诺兑现不了、没人敢改」的项目。** 核心算法（大纲 → 章节 → 写手 → 评估）是对的，缺陷集中在并发正确性、成本核算、一致性维护这三块。

## 四、详细分析

### 4.1 确凿缺陷中最值得立刻动手的 5 个

**A1 — 共享 `config` 的并发写竞争（`preactor.py:118-126`）**

```python
    # ── Step -1: Generate ending if user didn't provide one ──
    if not config.story_end.strip():
        logger.info(f"[版本 {version_id}] 未指定结局，生成戏剧性结局...")
        try:
            generated = await director.generate_ending(state)
            config.story_end = generated          # ← 写共享对象
```

`run_pre_actor`（`preactor.py:694-698`）把**同一个** `config` 实例传给所有版本任务：

```python
    for i in range(config.num_versions):
        task = asyncio.create_task(
            run_version(i + 1, config, token_budget, shutdown, progress_callback)
        )
```

后果有三层：(a) `num_versions=3` 且 `story_end` 留空时，**3 个版本各调一次 `generate_ending`**，同一个故事生成 3 个互相矛盾的结局；(b) 写入顺序取决于调度，最终生效的结局是随机的；(c) 后续所有 prompt 读 `self.config.story_end`，不同章节可能读到不同结局 → 故事内部自相矛盾。
**修法**：`generated` 存进 `state.config` 之前先复制 config，或者用 `dataclasses.replace(config, story_end=generated)` 生成版本私有副本。

**A2 — token 预算漏算 3~5 倍（`preactor.py:450-456`）**

```python
            # Update token budget
            est_chapter_tokens = write_tokens + 500  # rough estimate for other agent calls
            if not await token_budget.consume(est_chapter_tokens):
```

`+500` 是对「其他所有 Agent 调用」的估算。但一章实际发生：1 次 Director + 1 次 Protagonist（parallel 模式 N 次）+ 1~3 次 NPC + 1 次 Writer + 1 次 Memory 提取 = **5~7 次 LLM 调用**。Director 的 system prompt 约 2.5K token、user 约 1.5K、输出 1K；Protagonist 约 1.5K+1K；NPC 每次约 1.5K+0.5K；Memory 提取约 1.5K+0.5K。实际每章 ≈ 12K~15K token，而预算只记了 `write_tokens(~1.5K) + 500` ≈ 2K。**预算超支约 6 倍**，且 `preactor.py:209` 的 `token_budget.remaining < 3000` 提前熔断因此永远不会触发。
**修法**：`LLMClient.call` 已返回 `(text, tokens)`，把 `state.total_tokens_used += tokens` 的每一处改成同时 `await token_budget.consume(tokens)`。

**A3 — FastAPI 路由遮蔽（`webui/app.py:832` / `:893`）**

```python
@app.get("/download/{run_id}/{format}")          # ← 第 832 行，先注册
async def download_novel(run_id: str, format: str):
    ...
    if format not in FORMATS:
        raise HTTPException(status_code=400, detail=f"Unsupported format: format. Use: ...")
...
@app.get("/download/{run_id}/eval")              # ← 第 893 行，后注册
async def download_eval(run_id: str):
```

Starlette 按注册顺序匹配。`GET /download/abc/eval` 先命中第 832 行的路由，`format="eval"` 不在 `FORMATS`（`exporter.py:489`）→ 直接 400。**评估日志下载接口 100% 不可用**，且 `result.html` 里也没有指向它的链接（模板里只有 md/txt/epub/pdf 四个）。

**A4 — 命名 fallback 插值出函数对象（`naming.py:220-223`）**

```python
    fallbacks = [
        f"{p}的传奇", f"{p}战记", f"{p}：{theme}",
        f"{loc}故事", f"{event}", f"{p}与{loc}",
    ]
```

`p` / `theme` / `loc` / `event` 在上面 `generate_candidates` 里被定义成**函数**（`:127-131`），不是值：

```python
    def p(): return kw.protagonist or "主角"
    def loc(): return _random_pick(kw.locations, "远方")
    def theme(): return _random_pick(kw.themes, "命运")
    def event(): return _random_pick(kw.key_events, "冒险")
```

所以这 6 个 fallback 名字实际生成的是 `<function p at 0x7f...>的传奇`、`<function theme at 0x7f...>故事` 这类字符串（Python 的 f-string 对函数对象插值出 repr）。候选名池里混进这种垃圾，而 `score_and_pick`（`naming.py:425`）在 LLM 返回的名字匹配不上候选时会直接放行（`:462-464`），甚至在 LLM 失败时 `return candidates[0]`——垃圾名可能直接成为最终书名。**修法**：改成 `p()` / `theme()` / `loc()` / `event()`。

**A5 — provider 专属环境变量在 YAML 路径失效（`config.py:53-54`）**

```python
    # Resolve API key: file > env var
    api_key = data.get("api_key", "") or os.environ.get("SIFTED_INK_API_KEY", "")
```

而 `agents.py:159-172` 早就写好了 `resolve_api_key(provider, explicit_key)`（显式 > provider 专属 env > 通用 env），Web 端 `webui/app.py:571` 也正确调用了它。**只有 YAML 路径漏了**。README:96-104 与 `story_config.yaml:42` 都明确告诉用户 `export ANTHROPIC_API_KEY=...` 可用，示例 YAML 恰恰把 `api_key` 注释掉了 —— 照文档操作必然在 `config.py:95` 报「API key 不能为空」。

## 六、整体架构评估：**这套「多 Agent 并行预演」是过度设计**

### 立场：**是，当前的实现形态是过度设计。** 但请注意——我反对的不是「多 Agent」这个概念本身，而是**当前这套「每章 6~7 次 LLM 调用 × N 条完整故事线」的分解方式**。下面用代码证据说明。

### 6.1 证据一：Agent 的产出被下游丢弃，多 Agent 分解在信息瓶颈处失效

`NarrativeWriter.write_chapter`（`agents.py:1076-1155`）是唯一决定正文的地方，它拿到的输入是：

```python
        user = f"""{npc_intro_warning}{prev_context}
## 本章导演指示
{json.dumps(director_decision, ensure_ascii=False, indent=2)}
## 主角行动
- 行动类型: {protagonist_action.action}
- 情绪: {protagonist_action.emotion}
- 内容: {protagonist_action.content}
- 内心想法: {protagonist_action.metadata.get('inner_thought', '')}
{title_hint}
{style_note}
## NPC 行动
{npc_text or "本章无 NPC 参与行动"}
```

注意：Protagonist Agent 花一次 LLM 调用产出 150~300 字（`prompts.py:189`）的「行动」，NPC Agent 各产出 100~200 字，这些内容加起来约 500~800 字，**最终被写手重写成 650 字的正文**。而写手拿到的「导演指示」里，真正有约束力的只有 `scene_setting` 和 `chapter_summary` 两段文本——也就是说，**如果让写手直接读这两段文本，它可以写出同样的章节**。Protagonist / NPC Agent 的额外调用提供的是「装饰性结构」，不是「结构约束」。

更直接的证据：**导演被要求做分支决策，但分支从来不被使用**。`prompts.py:134-138` 要求导演输出 `branch_choice` 和 `branch_options`：

```python
  "branch_choice": "A",
  "branch_options": [
    {{"id": "A", "description": "分支A的走向描述"}},
    {{"id": "B", "description": "分支B的走向描述"}}
  ],
```

而全仓 grep `branch_choice|branch_options` 只有 4 处命中，**全部在 prompts.py 和 agents.py 的默认兜底字典里**（`agents.py:791-792`），**没有任何一处消费它**。所以 README:50 宣称的「每条情节线在关键分支点上做出不同选择」在代码里**根本不存在**——N 条「不同情节线」的实际差异来源只有：(a) 采样温度；(b) `preactor.py:322` 的 `random.choice(remaining)`；(c) `preactor.py:650-661` 的 7 条随机事件之一。**N=500 条预演里的绝大多数是同一份大纲的随机重采样。**

### 6.2 证据二：成本与产出的比例失衡

粗算（以 `target_word_count=8000`、`_adaptive_max_chapters` 封顶 15 章、`npc_mode=parallel` 每章 2 个 NPC 计）：

| 项 | 每章调用数 | 每章 token（估） |
|---|---|---|
| Director | 1 | ~5,000 |
| Protagonist | 1 | ~3,000 |
| NPC × 2 | 2 | ~4,000 |
| Writer | 1 | ~5,000 |
| Memory 抽取 | 1 | ~2,000 |
| **合计** | **6** | **~19,000** |

单条版本跑完 15 章 ≈ **285K token / 90 次调用**。`num_versions=3` → **855K token / 270 次调用**，产出 8,000 字。

对照「单 Agent 流水线 + 大纲/章节迭代」：
- 1 次大纲生成（~3K）+ 15 次写手（~5K/次）+ 1 次评估（~2K）≈ **80K token / 17 次调用**。
- 即 **3 条版本 ≈ 240K token**，与当前「1 条版本」的 285K 相当。

也就是说：**当前架构为了产出 3 个版本，付出的代价约等于单 Agent 架构产出 9 个版本**。如果单 Agent 流水线把同样的 855K 预算拿去跑「大纲 ×3 + 每份大纲迭代 3 轮」，得到的是 **9 份结构差异明确的大纲**，而不是 3 份「同大纲的随机变体」。

### 6.3 证据三：Agent 之间的协作全是单向的，编排复杂度远超收益

- Director → Protagonist → NPC → Writer，是一条**严格串行**的链（`preactor.py:226 → 277 → 331 → 357`），每一步都要等前一步的 LLM 返回。**这条链里没有任何一处「多 Agent 协商」或「投票」**——所谓「编剧室」实际上是「流水线」。
- 唯一的「协商」是**大纲竞优**（`preactor.py:132-160`：3 份大纲 → 1 次评估 → 选 1 份）。这才是这个项目里唯一真正有价值的 multi-agent 机制。
- 而这份大纲竞优**在每个版本里各做一遍**（`preactor.py:132` 在 `run_version` 内部）→ `num_versions=3` 时，同一个故事生成 9 份大纲、跑 3 次评估、选出 3 份可能不同的大纲。**这里才是应该共享的地方**，却恰恰是重复的。

### 6.4 结论与建议形态

**明确立场：保留「多版本择优」，砍掉「多 Agent 逐章流水线」。**

建议的目标架构（三层，从下往上）：

```
L1  大纲层（多 Agent 协作，保留）
    ├─ 3~5 个叙事角度并行生成大纲（这是真正有价值的并行）
    ├─ 评估器择优 + 人类可介入
    └─ 产出 1 份带里程碑的 StoryOutline   ← 全局共享，所有版本共用
L2  章节层（单 Agent 写手 + 轻量结构化约束，替换）
    ├─ 写手一次调用产出本章正文
    ├─ 约束来源 = 大纲里程碑 + 上一章 ChapterMemory + 活跃 NPC 档案
    │   （即把 Protagonist/NPC Agent 的产出从「正文前的独立决策」
    │     降级为「写手 prompt 里的结构化字段」，同一次调用里生成）
    └─ 每章 1 次写手 + 1 次记忆抽取 = 2 次调用（原来 6 次）
L3  评估层（保留，1 次调用/版本）
```

配套的并行策略改成：
- **大纲竞优在版本层做一次**（不再每版本各做一次）→ 省 2/3 的大纲开销。
- **N 条版本在「同一份大纲」下跑，差异来自「写作风格 / 叙事密度 / 结局处理方式」等 L2 层的可配置旋钮**（而不是靠温度碰运气），并且这才是「不同情节线」的实质。
- **每个版本可配置是否启用 Protagonist/NPC Agent**（`quality_mode="full"` 才开），默认关闭。

预期收益（同样 855K 预算）：
| 指标 | 当前 | 改造后（估算） |
|---|---|---|
| LLM 调用次数 | ~270 | ~55 |
| 有效大纲多样性 | 3 份（每版本重复生成 9 份） | 3~5 份（全局共享） |
| 版本间差异来源 | 温度随机 | 显式旋钮，可解释 |
| 每章 token | ~19K | ~7K |
| 可解释性 | 「为什么这条线更好」说不清 | 「这条线用的是什么旋钮组合」说得清 |

**必须承认的取舍**：砍掉 Protagonist/NPC Agent 后，**「角色自主决策」带来的文本多样性会下降**。这是真实损失。所以正确的做法不是直接砍，而是：
1. 先按上文把它降级为「写手 prompt 里的结构化字段」（一次调用同时产出决策与正文，**不额外花 token**）；
2. 在 `quality_mode="full"` 下保留独立的 Protagonist/NPC 调用，作为可选的「高成本模式」；
3. 用 A/B 对比（同一大纲、同一预算、单 Agent vs 多 Agent）实测文本评分，再决定默认值。**在做完这个实验之前，不应该宣称多 Agent 带来质量提升——目前没有任何证据支持这一宣称。**

### 6.5 什么**不**是过度设计（该保留的）

| `PROVIDER_REGISTRY` + `LLMClient` 统一适配层 | 13 家 provider 收敛到一个接口，扩展性极好，抽象是对的。唯一问题是它和业务 Agent 混在一个文件（R23）。 |
