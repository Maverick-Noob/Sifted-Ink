### 1.2 上下文里"看得见"却"用不上"的东西

`agents.py:764` 每章把主角状态 dump 进导演提示：

```python
- 当前主角状态: {json.dumps(state.protagonist_state, ensure_ascii=False)}
```

而 `state.protagonist_state` 的 6 个字段里，**只有 `emotional` 会被更新**：

```python
# preactor.py:404-405
state.protagonist_state["emotional"] = protagonist_action.emotion
```

`location`（`preactor.py:47`）只在开局写死一次 `"故事起始地点"`，此后 30 章不变；`physical` / `abilities_gained` / `key_items` / `relationships` **从未被任何代码写过**（全仓库 grep 确认）。

**后果（确凿缺陷）**：主角 agent 每章收到的状态面板永远是

```
- 情绪: 坚定
- 体力: healthy
- 位置: 故事起始地点
- 能力: 初始能力
- 重要物品: 无
```

主角**永远不知道自己拿到了什么神器、在哪个城市、谁跟他结盟**。这直接解释了为什么"角色成长"和"逻辑一致性"两个评估维度拿不到高分——**故事里的主角其实是个失忆的复读机**。

而 `story_memory.py` 明明已经抽出了 `ending_location` / `items_acquired` / `active_characters`（`story_memory.py:16-25`），**却从没回写进 `protagonist_state`**。修复成本：约 10 行。

### 2.2 是真"对话"还是各自独立生成？→ **各自独立生成 ❌**

这是本项目最影响成品质量的结构性问题。

**主角**（`agents.py:855-882`）生成时能看到的只有：导演的 `chapter_summary`、`scene_setting`、状态面板、**在场的 NPC 档案**（`_format_npcs`, `846-853`）。它不知道 NPC 会说什么。

**NPC**（`agents.py:896-948`）生成时能看到的只有：

```python
# agents.py:913-915
proto_info = ""
if protagonist_action:
    proto_info = f"\n主角刚才的行动: {protagonist_action.action} - {protagonist_action.content}"
```

注意这是**主角行动的"摘要字符串"**，不是主角在正文里说出的**台词原文**。而且所有 NPC 是**并行**跑的（`preactor.py:327-331`）：

```python
npc_tasks = [
    npc_agent.act(npc, state, scene_setting, protagonist_action)
    for npc in npcs_to_act
]
npc_results = await asyncio.gather(*npc_tasks, return_exceptions=True)
```

**结论**：一场戏里主角的台词、2 个 NPC 的台词，是 **3 次互不知情的独立生成**。写手最后拿到的是：

```python
# agents.py:1104-1106
npc_text = ""
for a in npc_actions:
    npc_text += f"- {a.agent_name} ({a.emotion}): {a.action} → {a.content}\n\n"
```

然后要靠写手把这些**互不对应的台词拼成一场对话**。结果必然是：

- 主角说完 A，NPC 回 B（不接茬）
- 两个 NPC 说的不是同一件事
- 写手被迫"转述"：把 `"我要走"` 转成"他表示自己执意要离开" ← **"转述腔"是 AI 味最典型的来源之一**

**高性价比修复**（不改调用数、几乎不增 token）：把 `preactor.py:327-331` 的 `asyncio.gather` 改成**有序串行**，并给 `NPCAgent.act` 增加 `recent_dialogue: list[str]` 参数，把前一个 NPC 的 `content` 追加进下一个 NPC 的上下文：

```python
# 改后（示意）
recent = []
npc_actions = []
for npc in npcs_to_act:
    a = await npc_agent.act(npc, state, scene_setting, protagonist_action,
                            recent_dialogue=recent)
    if a:
        npc_actions.append(a)
        recent.append(f"{npc.name}: {a.content}")
```

调用数 6/章 → 6/章，token +5% 以内，**对话连贯性提升一个量级**。

### 2.3 导演→正文的两段式：转述损耗

导演输出 `chapter_summary`（200-400 字，"用于引导其他 Agent 创作"，`prompts.py:132`），写手再把它**翻译成叙事**。中间隔了一层，导演的"意图"与最终文本之间必然有偏差，且写手会把它写成**摘要腔**而非场景。

**建议**：写手的 user message 里，把 `chapter_summary` 降级为"背景"（现在的 `## 本章导演指示` 段落），另外给一个 `## 本章必须出现的场景要素` 清单（由导演以结构化字段给出），让写手按要素"摆拍"而不是按散文"转述"。

### 2.5 「并行预演 500 版本」vs「1 条线深写 + 3 次大纲择优」

**先说事实：项目已经内置了"3 次大纲择优"。** `preactor.py:130-181`：每个版本内部先生成 3 份不同角度的大纲（`agents.py:385-389` 的 `OUTLINE_ANGLES`：角色驱动 / 悬念反转 / 史诗冒险），再用 `OUTLINE_EVALUATOR_PROMPT` 选优。**所以"3 次大纲择优"这个选项已经是默认行为。**

那么问题变成：**在同一 token 预算下，把预算从"更多版本"挪到"更深的单线 + 更好的收尾"值不值？**

| 方案 | token 预算 | 产出 | 关键风险 |
|---|---:|---|---|
| **A. 现状** 3 版本 × 20 章 | 67 万 | 3 条 1.2 万字独立线 | 版本同质（三份大纲里 LLM 各自可能收敛到相似解）；"版本 i 走不同分支"是假的（Q-18） |
| **B. 500 版本 × 20 章** | **1.10 亿** | 500 条 1.2 万字线，取 1 | ① 62,501 次 API 调用，**429 几乎必然**；`preactor.py:496-496` 的 429 处理是**直接终止整个版本**并标记 `terminated_early` → 而 `evaluator.py:24` 只承认 `reached_ending` 的版本 → **大批版本刚生成就出局，白烧 token**；② 1800s 超时（`preactor.py:198`）在供应商排队下会大面积触发；③ 边际收益递减 |
| **C. 1 版本 × 60 章** | 67 万 | 1 条 3.6 万字线 | 当前 RAG 只保留最近 3 章快照 + 5 条未解线索（`story_memory.py:34-35`），60 章后伏笔管理会崩；且只有 1 个样本，**无法择优**（评估器失去意义） |
| **D. 推荐**：3 版本 × 20 章 **+ 对优胜版本做 1 轮重写/润色** + 评估取 3 次中位数 + 真正启用 `branch_options` | 67 万 × 1.3 ≈ **87 万** | 3 条线 + 1 轮修订 | 需要 3 处小改动（启用 `NOVEL_POLISH_SYSTEM_PROMPT`、评估重采样、分支钉死） |

**量化 best-of-N 的边际收益**：

- 期望最大值随 log N 增长，N 从 3 → 500（167×）在 0-10 制上大约只换来 **+0.8 ~ +1.5 分**；
- 成本却涨 167×：Sonnet 口径从 ¥26 → **¥4,280**（见 §6）；
- **边际成本/边际收益 ≈ ¥2,800 / 分**；
- 而"重写润色"一轮（1 次 ~15K token 调用 + 1 次评估）成本约 **¥0.15**，对"逻辑一致性""角色成长"两个维度的提升是**直接、可控、可检查**的；
- 此外 500 版本会**主动降低**单版本质量：并发 500 意味着每章 6 次调用打到供应商，429/超时是主要失效模式，而**失效的版本在 `evaluator.py:24` 被直接判死**——你烧掉 1.1 亿 token 却可能一个可用版本都选不出来。

**结论：500 版本是"烧钱换噪声"。建议 `num_versions ≤ 5`（默认 3），把省下的预算投到「深写 + 修订 + 评估重采样 + 真分支」。** 这与 `03-产品需求与UX.md` 的结论一致，但本篇补上了**量化的成本/收益比**。

### 3.1 实现方式 → **纯 LLM 打分，无任何规则**

```python
        choice = await _user_select(completed_evals, shutdown)
        result.winning_version_id = choice
        result.user_selected = True
    else:                # Web UI：自动选最高分
        result.winning_version_id = completed_evals[0].version_id
        result.user_selected = False
else:
    result.winning_version_id = completed_evals[0].total_score  # 最高分
```

- 排序键 = `total_score`（= 四维平均）✅
- Web UI 走 `interactive=False`（`webui/app.py:168`）→ **直接取 `completed_evals[0]`，即最高分** ✅
- CLI 走 `interactive=True` → 分数差距 ≥5% 时自动取最高分；<5% 时交给用户 ✅
- `writer.py:331-336` 的 `_get_winning_version` 按 `winning_version_id` 取版本 ✅

**唯一的例外**：`evaluator.py:66-76` 的兜底分支——**没有任何版本完成时**，选的是 `max(result.versions, key=lambda v: v.chapter_count)`（**章节数最多的**），而不是分数最高的。这是**语义降级**（此处无分数可比），但应该记进 `eval_log` 标注"降级选择"。

### 3.3 但"一致"不等于"可信"——6 个可信度缺陷

| # | 缺陷 | 严重度 | 证据 |
|---|---|---|---|
| E-1 | **绝对分跨调用不可比**。每个版本是**独立的一次 API 调用**（`evaluator.py:46-52` 串行循环），LLM 在不同调用里的 0-10 标尺没有校准。A 调用里的 7.5 与 B 调用里的 7.5 不是同一把尺。**跨版本排序在统计上不可靠**。 | 高 | `evaluator.py:46-52` |
| E-2 | **泄漏版本标识**。user message 里写死 `- 版本 ID: {state.version_id}`。模型知道这是"版本 1/2/3"，存在**位置与标签偏见**（常见偏好在最后一个 / 在有"3"的版本）。 | 中 | `agents.py:974-978` |
| E-3 | **无长度归一**。更长的版本天然有更多情节、更容易凑出"冲突升级""反转"，因此在 `dramatic_tension` 上系统性占优。三个版本的章节数若不同（很常见：早早 `ending_reached` 的版本只写 8 章），比较即失真。 | 高 | `agents.py:962-983` 无截断 |
| E-4 | **无 rubric 锚点**。提示只给了维度定义（`prompts.py:319-325`），要求输出 0-10 且带一位小数（`336-339`）。模型返回 7.5 / 8.0 这类**伪精度**，实际分辨率远达不到 0.5 分。 | 高 | `prompts.py:317-345` |
| E-5 | **不可复现**。`temperature=0.3`（`agents.py:985`）、无 seed、无缓存。同一个版本两次评估可差 0.5~1.0 分。而选版阈值是 **5%**（`evaluator.py:91`），在 0-10 制上 5% × 8.0 = **0.4 分** → **几乎必然触发"分数接近"**，把选择权推给 CLI 菜单——而那个菜单只显示每版最后 100 字（`evaluator.py:109`）。 | 高 | `agents.py:985` + `evaluator.py:91,109` |
| E-6 | **解析失败静默给 5.0**。JSON 解析失败时四维全部填 5.0（`agents.py:990-1000`），总分 5.0，**看起来像一个"中等偏下但合法"的分数**，而不是"评估失败"。若两个版本都失败，排序完全随机。 | 中 | `agents.py:989-1000` |

### 3.4 四维能否区分版本？

**能，但区分度很差，且区分的往往不是质量。** 原因：

1. 四维**高度共线**——一个"AI 味重、逻辑平"的版本，四个维度会一起给 5-6 分，因为 LLM 实际上在给"整体印象分"再拆成四项；
2. `ending_alignment` 高度可预测：只要导演在最后一章写了 `ending_reached: true` 并复述了目标结局，这一项就接近满分，**几乎不携带区分信息**；
3. `character_growth` 需要跨全文追踪弧线，而评估器**只看成品文本**、看不到主角的设定与状态轨迹（`agents.py:980-981` 虽给了 traits，但只是静态字符串）；
4. 真正能区分版本的两件事——**章末钩子质量、对话自然度、AI 味**——**四个维度一个都没覆盖**。

### 3.5 评估器改进方案

**P0：改成 pairwise 相对评估（成本持平，判别力显著提升）**

对 N 个版本做轮转两两比较，用胜场（Borda）定排名：

```
新增 prompts.py: EVALUATOR_PAIRWISE_PROMPT
新增 agents.py:  EvaluatorAgent.compare(state_a, state_b) -> {"winner": "A"|"B"|"tie", ...}
新增 evaluator.py: _round_robin_rank(states) -> list[version_id]
```

- N=3 时两两比较 3 次 ≈ 现在 3 次独立打分，**成本持平**；
- 每次比较**打乱左右顺序跑两遍**（A/B 与 B/A），只有两次结论一致才计分 → **消除位置偏见**；
- 新增 `prompts.py` 模板（改写前后见 §1.3 P-8）。

**P1：给 rubric 加锚点（把伪精度变成真分辨率）**

`prompts.py:319-325` 的维度定义后追加锚点表，例如：

```
- **戏剧张力**
  - 3 分：只有背景冲突，无升级
  - 6 分：冲突有 2 次以上升级，但无反转
  - 8 分：冲突有升级且至少 1 次反转，代价有变化
  - 10 分：多层冲突交织，反转改变读者对前文的理解
```

并要求**每个分数必须附 evidence（引用原文 ≤30 字）**，无证据的分数视为无效（见 §1.3 P-7）。

**P2：多次采样取中位数**

每个版本评估 3 次（可换 `user` 消息的段落顺序 / 用不同措辞的 prompt 变体），**取中位数**而不是均值（中位数抗离群）。成本 ×3（评估阶段只占总成本 6%，可接受）。

**P3：长度归一**

评估前把所有版本截断到**相同章数**（如都取前 15 章）或按 `count_chinese_chars` 归一；或在维度里新增"信息密度"并从 `dramatic_tension` 中剥离长度红利。

**P4：`ending_alignment` 改为 gate 而非 1/4 权重**

用户明确指定了结局，它应当是**硬约束**而不是四分之一的分数：

```python
# 建议（evaluator.py）
if ev.ending_alignment < 6.0:
    ev.disqualified = True   # 结局不达标的版本不参与排名
```

现在的实现里，一个"结局完全跑偏但其它三维 9 分"的版本可以靠平均分胜出（`agents.py:1002-1007`），**这是明确的逻辑漏洞**。

**P5：阈值从"5% 相对差"改为"绝对差 + 置信区间"**

```python
# 现在（evaluator.py:91）
if top_score > 0 and (top_score - second_score) / top_score < 0.05:

# 改后
gap = top_score - second_score
if gap < 0.5:          # 绝对差 < 0.5 分才认为"接近"
    ...
```

因为 0-10 制上 5% 只有 0.4 分，**几乎每次都进"接近"分支**。

**P6：解析失败必须可区分**

`agents.py:989-1000` 的兜底改为 `is_complete=False` 或加 `eval_failed=True` 字段，并在 `evaluator.py` 里把失败版本**排除出排名**（而不是让它以 5.0 分参与排序）。

**P7：新增"网文专项"维度（与四维并行，不加权）**

在评估里加两个**只做诊断、不参与排名**的指标：

- `hook_quality`：末章最后 100 字是否留下未解答的问题（0-10）
- `ai_slop_score`：命中禁用词表的次数（0-10，越低越好）

这两项直接对应"AI 味"和"追读欲"，是本项目真正缺的标尺。

## 4. RAG 记忆（story_memory.py）

### 4.1 它其实不是 RAG

`story_memory.py:1-7` 的 docstring 自称 "Lightweight RAG story memory"，但实现是**规则式的结构化快照**：

- **抽取**：`extract_chapter_memory`（`story_memory.py:146-184`）用 LLM 从**章节最后 1500 字**（`157`）抽 9 个字段；
- **检索**：`build_context`（`story_memory.py:63-117`）是**固定顺序的硬编码拼接**，**没有向量、没有相似度、没有 top-k 排序、没有阈值**；
- **检索内容**只有 5 块：上一章结尾快照（`71-83`）、最近 3 章摘要（`85-94`）、未解线索（`96-102`）、NPC 首登场记录（`104-111`）、当前活跃 NPC 名（`112-115`）。

> 严格说，"R"（retrieve）这一步是**缺失**的——`build_context` 不针对任何 query 做检索，是"永远取固定的几块"。在 30 章规模下这可以接受，但**它无法回答"这一章需要回忆哪条旧线索"这个真问题**。

### 4.2 抽取的字段（`story_memory.py:14-25`）

| 字段 | 质量评价 |
|---|---|
| `ending_location` | 最有价值的一个（衔接必需），但**从未回写进 `protagonist_state`**（见 Q-05） |
| `active_characters` | 抽取了但只在"在场角色"一行展示，**没有实体归一** |
| `key_events` | 实用 |
| `unresolved_threads` | **最关键也最脆弱**（见 4.4） |
| `emotional_state` | 实用 |
| `new_npcs_introduced` / `npcs_exited` | 实用，但只用于展示"第 N 章首次登场" |
| `items_acquired` | 实用但**不回写主角状态** |
| `scene_summary` | 实用 |
| **缺失** | **无时间线**（故事内日期/时刻）、**无伏笔回收状态**、**无人物关系图**、**无别名表**、**无已解决线索** |

### 4.3 检索机制：无

无向量库、无 embedding、无 BM25、无 top-k 排序、无相似度阈值。唯一的"检索"是 `get_unresolved()`（`story_memory.py:45-52`）和 `get_npc_intros()`（`54-61`），两者都是**全量扫描 + 硬截断**。

### 4.4 确凿缺陷：`get_unresolved()` 的 `[-5:]` 会永久丢弃最早的伏笔

```python
# story_memory.py:45-52
def get_unresolved(self) -> list[str]:
    """Get all unresolved threads still pending resolution."""
    threads = []
    for m in self.memories:
        for t in m.unresolved_threads:
            if t not in threads:
                threads.append(t)
    return threads[-self.max_unresolved:]     # ← 保留最后 5 条
```

逻辑推演：

1. `threads` 按**章节顺序**累积（第 1 章埋的线索排在索引 0）；
2. 未解决的线索按定义会**持续存在**——它们不会被移除，只会每章被重复抽取；
3. 因此 `threads` 会单调增长，而 `[-5:]` **永远只返回最近加入的 5 条**；
4. **第 1~3 章埋下的伏笔，一旦第 6 条新线索出现，就永远消失在检索窗口外**；
5. 伏笔的回收依赖写手"记得"它——而它根本没被写进 prompt。

**这与"伏笔—回收"机制完全相反**：越是重要的、埋得越早的伏笔，越不可能被回收。

**修复**（把"最近"改成"最紧急"）：

```python
def get_unresolved(self, current_chapter: int) -> list[str]:
    # 记录每条 thread 首次出现章号，按「紧迫度」排序
    ranked = []
    for m in self.memories:
        for t in m.unresolved_threads:
            if t not in [r[0] for r in ranked]:
                ranked.append((t, m.chapter_num))
    # 埋得越久越紧迫（越可能该收了）
    ranked.sort(key=lambda x: x[1])
    return [t for t, _ in ranked[:self.max_unresolved]]
```

更好的做法见 §4.8 的"伏笔台账"。

### 4.5 遗忘机制：没有

`StoryMemoryStore.memories` 只增不减（`story_memory.py:35,39-40`），但 `build_context` 只用最近 3 条（`86`）。于是 30 章后，**第 1~27 章的所有事件、伏笔、物品信息在写手上下文里彻底消失**——没有滚动摘要、没有归档、没有"重要事实常驻"。

### 4.6 冲突解决机制：没有

| 冲突类型 | 现状 | 后果 |
|---|---|---|
| **同名不同人** / **同物不同名** | 导演自由命名（`npc_name_style=default`），`naming.py` 的名字生成器**只用于书名和章节标题**（`naming.py:325`），不参与 NPC 注册 | "炎之心" / "火种之炎" 被当成两件东西；同名 NPC 覆盖 |
| **重复埋设伏笔** | `unresolved_threads` 只做**去重**（`if t not in threads`），不同措辞的同一伏笔会存两份 | 伏笔台账膨胀、回收时不知道该收哪条 |
| **设定冲突** | `world_setting` 是静态字符串，每章原样重复注入 | 与剧情发展出的新设定矛盾时，无人裁决 |
| **已解决线索复活** | 无 `resolved_threads` 字段 | 已回收的线索下一章又被当"未解线索"注入 → 反复提醒读者一个已经结束的悬念 |

### 4.7 跨章一致性：四项全无保障

| 一致性维度 | 能否保证 | 说明 |
|---|---|---|
| **人名** | 否 | 无 canonical 注册表；`get_npc_intros` 用精确匹配（`story_memory.py:59`），别名即失效 |
| **设定** | 否 | 静态字符串，冲突不裁决 |
| **时间线** | 否 | **完全没有时间字段**。`ChapterMemory` 无 `story_day`；"三天后""次日黄昏"这类跳跃无法被追踪或校验 |
| **伏笔** | 否 | 见 4.4，只埋不收 |

### 4.8 RAG 改进方案

**R-1（必做，成本 0）：修 `get_unresolved` 的排序 + 加 `resolved_threads`**

在 `MEMORY_EXTRACTION_PROMPT`（`story_memory.py:124-143`）里增加两个字段：

```json
"resolved_threads": ["本章被回收的线索（请原样引用之前的描述文字）"],
"timeline": {"story_day": 3, "time_of_day": "黄昏", "elapsed": "距上章过去两天"}
```

`ChapterMemory` 加 `resolved_threads` 与 `timeline` 字段；`get_unresolved` 排除已回收项并按紧迫度排序。

**R-2（必做，成本 0）：建立实体注册表 + 别名归一**

在 `StoryMemoryStore` 里加 `self.registry: dict[str, str] = {}`（alias → canonical）；抽取时让 LLM 额外输出 `entities: [{"canonical": "炎之心", "aliases": ["火种之炎", "父亲的遗物"]}]`；`build_context` 输出"实体注册表"段，写手据此知道"火种之炎"就是"炎之心"。主角/物品的 canonical 名一旦确定，后续章节强制使用。

**R-3（必做，成本 0）：把记忆回写进 `protagonist_state`**

```python
# preactor.py:388-394 附近
mem = await extract_chapter_memory(narrative_text, chapter.number, client)
memory_store.add(mem)
state.protagonist_state["location"] = mem.ending_location or state.protagonist_state["location"]
if mem.items_acquired:
    state.protagonist_state["key_items"] = list(dict.fromkeys(
        state.protagonist_state["key_items"] + mem.items_acquired))
if mem.emotional_state:
    state.protagonist_state["emotional"] = mem.emotional_state
```

**这一步同时修掉 Q-05（主角状态是死的）和 Q-08（伏笔取 `[-5:]`）两个确凿缺陷。**

**R-4（高价值，省 17.8% token）：把记忆抽取合并进导演输出**

导演本来就在输出 `chapter_summary` / `npc_instructions` / `milestone_reached`；让它的 JSON 多输出一个 `memory` 字段（`ending_location` / `key_events` / `unresolved_threads` / `items_acquired`），即可**完全省掉每章 1 次记忆抽取调用**（`story_memory.py:163`）：省 1 次调用/章（6 → 5）、省 17.8% token。额外好处：导演与记忆**同源**，不会出现"导演说 A、记忆抽取说 B"的分裂。

**R-5（长篇必需）：滚动摘要代替硬截断**

每 5 章把前 5 章压成 200 字卷摘要，存为 `arc_summaries`；`build_context` 输出"已发生的故事梗概（压缩版）"，解决 30 章后早期设定消失的问题。

**R-6（中）：从规则检索升级为意图检索**

让抽取阶段给每条 key_event / unresolved_thread 打**场景标签**（"战斗""谈判""探索""情感"）；导演输出 `scene_setting` 时同时输出 `scene_tags`；`build_context` 按标签 + 关键词匹配相关历史，**取代当前的"最近 3 章 + 最后 5 条"固定窗口**。

**R-7（中）：伏笔台账带状态与期限**

```python
@dataclass
class PlotLoop:
    id: str
    text: str
    planted_chapter: int
    priority: int          # 1-3
    status: str            # open / resolved / abandoned
    due_chapter: int       # 建议回收章
```

导演每章输出 `loops_resolved: ["id"]`；超过 `due_chapter + 3` 仍 open 的伏笔，导演必须显式 `abandon`（写明"因 X 放弃"），否则计入评估的"逻辑一致性"扣分。**这是把伏笔管理从祈祷变成流程。**

## 5. 长篇一致性机制

### 5.1 三幕结构：定义与实现不一致

| 位置 | 划分 |
|---|---|
| `prompts.py:20-23`（大纲提示） | 第一幕 25%~30%，第二幕 40%~50%，第三幕 20%~30% |
| `agents.py:625-644`（`_calc_pacing`） | 铺垫期 <30%，发展期 30%~50%，高潮期 50%~75%，收束期 ≥75% |

**两套阈值不一致**（30/50/75 vs 25-30/40-50/20-30），而且 `_calc_pacing` 的划分是**纯章节比例**驱动的，**与剧情进度无关**——即使故事还在铺垫阶段，到第 16 章（16/20=80%）也会进入"收束期 禁止新角色"。

### 5.2 确凿缺陷：里程碑"到章号即自动达成"→ 全部进度控制失效

```python
# preactor.py:421-431
# Also check if chapter number passed any milestone targets without explicit marking
if state.outline:
    for m in state.outline.milestones:
        if not m.reached and chapter.number >= m.target_chapter:
            # Auto-mark if the chapter is somewhat close to the target
            m.reached = True
            progress_made = True
            logger.info(f"[版本 {version_id}] 自动达标: {m.description[:60]} ...")
```

**只要章节号 ≥ 目标章号，里程碑就无条件标记为达成**——不看剧情里到底发生没发生。连锁后果：

1. **`reached` 字段 100% 失真**。它反映的只是"时间到了"，不是"剧情到了"。
2. **停滞检测彻底失效**。`state.chapters_without_progress`（`preactor.py:434-437`）靠 `progress_made` 重置；而 `progress_made` 在章节号越过目标时必然为 True → 计数器几乎永不清零 → `agents.py:672-676` 的"连续 N 章没有达到任何里程碑"警告**几乎不触发**。
3. **导演看到的进度全是绿勾**：
   ```python
   # agents.py:753
   status = "✅" if m.reached else "⬜"
   ```
   导演收到的用户消息里，大纲节点**大半已被标绿** → 它不知道该往哪推 → 只能自由发挥 → **注水、跑题、重复**。这是"故事后半程失控"的直接机制。
4. **唯一的真实路径几乎不走**：
   ```python
   # preactor.py:411-419
   if milestone_reached and state.outline:
       for m in state.outline.milestones:
           if not m.reached and m.description[:30] in milestone_reached:
   ```

**修复**：删掉 `preactor.py:422-431` 的自动达标分支，改为**语义判定**——用 LLM 判断本章事件是否覆盖了某里程碑（可合并进 R-4 的导演输出，零额外调用），或用关键词/实体匹配。至少也要改成"章节号超过目标 +3 才标记为'已错过'，不算达成"。

### 5.5 重复动作检测（相似度 > 0.9 连续 3 次）：阈值不合理

```python
# utils.py:78-106
def detect_repeated_action(actions, text_getter, threshold=0.9, window=3) -> bool:
    recent = actions[-window:]
    texts = [text_getter(a) for a in recent]
    similar_count = 0
    for i in range(len(texts)):
        for j in range(i+1, len(texts)):
            if text_similarity(texts[i], texts[j]) > threshold:
                similar_count += 1
    total_pairs = window * (window - 1) / 2        # = 3
    return similar_count >= total_pairs * 0.5      # = 1.5 → 实际需 ≥2 对
```

**反例（举 4 个）：**

| # | 场景 | 结果 | 分析 |
|---|---|---|---|
| 1 | 连续 3 章都写"林远走进城门"，但措辞不同：*踏入城门* / *来到城门前* / *站在城门口* | **不触发**（ratio 约 0.3~0.5） | **假阴性，且命中的是最典型的 AI 换皮复读**。语义重复不等于字面重复，`difflib` 抓不到 |
| 2 | 3 个 NPC 同时 JSON 解析失败，全部走兜底文案 `{name} 静静地观察着周围的一切。`（`agents.py:934`） | **触发**（ratio = 1.0） | **假阳性**，而且触发的原因恰恰是"上游已经出错了"，此时再注入随机事件只会雪上加霜 |
| 3 | 规格说"连续 3 次"，实现是"3 次里任意 2 对相似" | 语义不符 | `>= 1.5` 意味着 2/3 相似即报警，比"连续 3 次"激进得多；且 `text_getter` 把**动作类型**也拼进文本（`constraints.py:80-81`：`f"{a.action}: {a.content}"`），同类型动作天生相似度更高，进一步抬高误报 |
| 4 | 主角 content 极短（如 `observe: 等待`）连续 3 次 | 触发 | 短字符串 ratio 极易 > 0.9 |

**更严重的后果**：一旦触发，系统注入的是**固定 7 条模板**（`preactor.py:653-660`）：

```python
events = [
    "突然，一道闪电劈开了天空，暴雨倾盆而下，迫使所有人寻找避难所。",
    "远处传来一声巨响，地面开始震动——有什么巨大的东西正在接近。",
    "一个陌生的信使出现在面前，手中拿着一封火漆密封的信件。",
    ...
]
```

并**原样塞进正文指令**（`preactor.py:230-233`）：

```python
director_decision["chapter_summary"] += (
    f"\n（系统干预：检测到重复模式，强制加入随机事件：{force_event}）"
)
director_decision["scene_setting"] = force_event
```

**这是 AI 味的直接生产源**：全书反复出现"突然，一道闪电劈开了天空"。任何读过网文的读者都会立刻出戏。

**修复建议**：

1. 阈值从 0.9 降到 **0.72**，并改用 **2-gram 集合的 Jaccard**（对中文更稳），同时**排除动作类型前缀**；
2. 语义重复用**关键词指纹**兜底：对 content 抽 3-gram 集合，Jaccard > 0.5 也算重复；
3. **把 7 条固定模板换成 LLM 生成的情境化事件**（复用导演的一次调用，让它输出 `forced_event` 字段），或至少扩充到 30+ 条多样化模板，并**禁止使用"突然/忽然"开头**；
4. 修 `>= total_pairs * 0.5` 为 `>= total_pairs`（真正要求 3 次全像）或 `>= total_pairs * 0.8`。

### 5.6 章节字数控制 vs `max_tokens_per_call = 4000`

**先算 token**（Claude 中文 tokenizer 假设，见 §6 假设表）：

- Claude 3/4 对中文常用字大多 **1 token 约 1 字**，少数生僻字 2 token；保守按 **0.7~1.0 token/字**；
- 因此 **4000 max_tokens 约 2,800 ~ 4,500 汉字**（中位约 3,500 字）；
- 章节目标 500~800 字 → 需 **500~1,150 token**，**余量约 4 倍，不构成瓶颈**。

**所以矛盾不在 token 上，而在"字的口径"上——三处互相打架：**

| # | 位置 | 口径 |
|---|---|---|
| 1 | `agents.py:1055`（写手**系统**提示） | "字数控制在 **500-800 字**"（硬编码） |
| 2 | `agents.py:1147`（写手**用户**消息） | "**目标字数: {word_target} 字**"，动态计算，可能 = 320 或 = 1,200 |
| 3 | `models.py:194`（`total_words`） | `sum(len(ch.content))` = **字符数（含标点、空行）**，不是字数 |

后果：

- 写手同时收到 500-800（系统）与 320/1200（用户）两个指令 → **模型通常服从系统提示** → 实际每章约 600 字；
- 20 章 × 600 = **12,000 字符**，而目标写的是 8,000 → **超 50%**；若 `word_target` 生效（1200 字/章）则是 24,000 → **超 200%**。**两个方向都可能，且完全不可预测。**
- 界面上的"字数"显示的是**字符数**（`webui/app.py:309,329,692` 直接用 `v.total_words`），用户看到的 12,000 "字"里其实只有约 9,600 个汉字。

**另一个隐藏的截断点**：

```python
# agents.py:1153-1154
text, tokens = await self.client.call(
    self._build_system_prompt(), user, max_tokens=3000, temperature=0.9
)
```

写手**硬编码 max_tokens=3000**。而 `agents.py:264` 会取 `min(requested, config.max_tokens_per_call)`：

- 用户把 `max_tokens_per_call` 调到 2000 → **写手被静默压到 2000 token（约 1400~2000 字）**，目标 1200 字时可能刚好截断，且只在日志里 warn（`agents.py:1158-1165`）；
- 反过来把 `max_tokens_per_call` 调到 8000，写手也只拿 3000 → **配置对写手无效**。

**修复**：

1. 写手系统提示的"500-800 字"改为"**以用户消息中的目标字数为唯一准绳**"；
2. 统一用 `utils.py:348` 已有的 `count_chinese_chars` 统计字数，替换 `models.py:194` 的 `len()`；
3. `max_tokens` 改为按 `word_target` 动态计算：`int(word_target * 1.6) + 300`（留 1.6 倍余量应对截断与标点），并设下限 800；
4. 在 `writer.write_chapter` 返回时**校验实际字数**，若低于目标的 70% 触发一次"扩写"重试（可复用同一 prompt，追加"请扩写到 N 字"）。

### 5.7 NPC 清理规则（3 章未活跃）：会误杀重要角色

```python

def _auto_prune_npcs(state, version_id, config):

    inactive_threshold = 3

            candidates.append((npc, f"已 {chapters_inactive} 章未活跃"))
        elif npc.relevance == "low" and chapters_inactive >= 2:
            candidates.append((npc, f"低相关性 NPC，{chapters_inactive} 章未活跃"))
    min_keep = min(2, len(state.active_npcs))
    ...
```

**缺陷 1（严重）：`last_active_chapter` 只在 NPC 产生行动时更新**

```python

for npc in npcs_to_act:
    if npc.name == result.agent_name:
        npc.last_active_chapter = state.chapter_count + 1
```

而每章只有 **2~3 个** NPC 行动（`preactor.py:316-323`：`npcs_to_act = high_rel[:2]` + 随机 1 个 medium）。

**反例**：`max_npcs=30`，每章 3 个 NPC 行动 → 一个 `relevance="high"` 的**导师**平均 **10 章**才轮上一次发言；第 5 章时 `chapters_inactive = 4 > 3` → **被自动清理**。而它恰恰可能是第 8 章的关键线索提供者。**"在场但没轮到说话"被等同于"已经离场"。**

**缺陷 2（致命）：`npc_mode="narrator"` 模式下所有 NPC 会被清空**

```python

    # Fastest: no NPC agent calls, narrator handles all NPC描写
    npcs_to_act = []
```

此时**没有任何 NPC 产生行动** → `last_active_chapter` 永不更新 → 每个 NPC 都在 `intro_chapter + 4` 被清理 → **第 5 章之后活跃 NPC 恒为 0**。这是低成本档最容易踩的坑。

**缺陷 3（提示词与代码不一致）**：`prompts.py:98` 对导演说"已 3 章以上未出场的 NPC"应被清理，代码是 `chapters_inactive > 3`（即 4 章）。

**缺陷 4（数量三处矛盾）**：

| 来源 | 数量 |
|---|---|
| `prompts.py:102`（给导演看） | 建议 5~8 人 |
| `prompts.py:103` / `story_config.yaml:49` | 上限 30 |
| `preactor.py:628`（代码下限） | `min_keep = 2` |

**缺陷 5（误伤用户指定角色）**：用户通过 `user_npcs` 定义的 NPC（`preactor.py:96-115`）**没有 `relevance=high` 的保护**，同样会被自动清理——用户明确要求出场的角色，5 章后就没了。

**修复建议**：

```python
# preactor.py:604 附近
def _auto_prune_npcs(state, version_id, config):
    current_chapter = state.chapter_count
    candidates = []
    for npc in state.active_npcs:
        if not npc.alive or not npc.active:
            continue
        # ① 用户指定角色永不自动清理
        if npc.user_defined:
            continue
        # ② relevance=high 需导演显式 remove 才可清理
        if npc.relevance == "high":
            continue
        # ③ 「活跃」定义为"在场"，不是"本轮被选中行动"
        chapters_inactive = current_chapter - max(
            npc.last_active_chapter, npc.last_present_chapter
        )
        if chapters_inactive > 3:
            candidates.append((npc, f"已 {chapters_inactive} 章未在场"))
        elif npc.relevance == "low" and chapters_inactive >= 2:
            candidates.append((npc, f"低相关性 NPC，{chapters_inactive} 章未在场"))
```

配套：在导演决策里增加 `npc_present: ["名字", ...]`（导演本来就在写 `scene_setting` 和 `npc_instructions`），用它更新 `npc.last_present_chapter`。**这是零额外调用的修法。**

另外把 `min_keep` 提到 4（与"5~8 人"对齐），并把 `prompts.py:98` 的"3 章"改成"4 章"以与代码一致。

### 7.5 结构化改造建议

**目标：把"形容词堆砌"改为"可执行的风格规格"。**

**方案 A（推荐）：双文件分离 + 离线 LLM 生成 + 人工审校**

把现在的 `writing_style.json` 拆成两个：

- `writing_style.json`（保留）：`name` / `region` / `bio`（现 `style`，纯文学史）/ `representative_works` / `death_year` / `is_public_domain` / `pd_jurisdiction` / `risk_tier`
- `writing_style_specs.json`（新增）：**可执行规格**，由一个**离线脚本**（一次性调用 LLM，把 bio + 2 个代表作品 → 规格 JSON）批量生成，再人工抽检 20%。

**方案 B（轻量）：就地扩字段**，给每个条目加 `spec` 对象。优点是不动读取逻辑。

无论 A/B，**规格 schema 至少包含这 8 类可执行参数**：

| 字段 | 类型 | 示例 | 为什么要 |
|---|---|---|---|
| `narrative_person` | enum | 第三人称有限 | 视角一致性 |
| `viewpoint_distance` | enum | 近/中/远 | 决定"代入感"强弱 |
| `sentence_length` | {p50, p90} 字 | 鲁迅 12/24；天蚕土豆 16/30 | **最能区分风格的单一参数** |
| `paragraph_length` | {p50, p90} 句 | 1.5/3 | 决定"碎"还是"整" |
| `dialogue_ratio` | float | 鲁迅 0.30；网文 0.45 | 网文最关键指标 |
| `description_ratio` / `psychology_ratio` | float | 0.25 / 0.10 | 防"景物抒情+内心戏"灌水 |
| `vocabulary` / `imagery` | string[] | ["日常器物","街巷实景"] | 意象偏好 |
| `forbidden` | string[] | ["心中五味杂陈","嘴角勾起"] | **AI 味黑名单** |
| `prefer` | string[] | ["用具体名词替代抽象形容词"] | 正面引导 |
| `sample_paragraph` | string（120~200 字） | 见下 | **唯一能真正传达"质感"的东西** |

**关键洞察：`sample_paragraph` 比任何参数都重要。** 参数可以给模型指路，样例才能给模型"手感"。建议每条风格配一段 150 字左右的**自撰**（非原作）示范片段。

## 11. 最终判断

**这个项目离"能写网文"还差什么？**

不是模型能力，不是 token 预算，也不是 Agent 数量。是三样东西：

1. **把"网文"翻译成可执行规格**。目前所有提示都在说"写得好一点""有戏剧张力""像某位作家"——全是不可验证的形容词。网文是可量化的：对话率、段长、章末 100 字是不是钩子、爽点密度、每章节拍数。**把 P-1 / P-2 / P-7 三条落地，AI 味会立刻下降一个档次，成本为零。**

2. **让 agent 之间真的说话**。现在是"导演写计划 → 主角各说各的 → NPC 各说各的 → 写手圆场"。改成串行 + 传台词原文，调用数不变、token 增 5%，**对话连贯性提升一个量级**。

3. **修掉那 4 个静默失效的 bug**（Q-01 里程碑、Q-03 NPC 误杀、Q-05 主角状态、Q-08 伏笔截断）。它们**不报错、不告警**，只是让一致性慢慢塌掉，最终在评估器上表现为"逻辑一致性 6.5 分"，而没人知道原因。

**关于 500 版本**：不建议。它把 1.1 亿 token 变成 1 部 12,000 字小说，边际收益 +1 分，边际成本 ¥2,800/分。**同样的钱花在"提示词加网文技法 + 一轮重写润色 + 评估重采样"上，收益高 1~2 个数量级。** 而且 500 并发会主动提高 429 率，失败版本在 `evaluator.py:24` 直接出局——**你可能烧完全部预算却连一个可选的版本都没有**。

**最低成本的高杠杆动作（今天就能做，约 100 行代码 + 3 段提示词）**：
1. 删 `preactor.py:422-431`；
2. 记忆回写 `protagonist_state`（约 10 行）；
3. 修 `get_unresolved` 排序（约 5 行）；
4. NPC 改串行 + 传台词（约 15 行）；
5. 写手提示加"三件套 + 禁用词表 + 一个 few-shot"（约 40 行提示词）。
