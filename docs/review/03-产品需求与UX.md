## 0. 一页纸结论

| 维度 | 结论 |
|---|---|
| **它现在是什么** | 一个**中短篇小说的一次性批量生成器**（8 千～3 万字），附带多 Agent 编排、四维自动打分、6 种导出格式。 |
| **它应该是什么** | 一个**网文写作者的「情节决策 + 章节工作台」**：预演的价值不是烧 token 选出唯一答案，而是**把可能的走向摆给人看让人拍板**，然后**支持人在每一章上继续写**。 |
| **价值主张是否成立** | **部分成立，但当前实现方式不成立。** 「并行 500 条情节线」在代码里**不是 500 条不同情节线**（见 §4.2 三条硬证据）；「择优」是**同一个 LLM 自评**，判别力远低于人。**建议：推翻「自动择优 + 一次性成书」的实现，保留「多走向显式化」的产品意图。** |
| **最大单点风险** | **无法产出真正的长篇网文。** 章节上限 30 + 每章字数天花板 1,500 字 ⇒ 理论产出上限约 4.5 万字，而目标字数填 30 万时会被**静默截断到 15%**，界面毫无提示。 |
| **最大体验灾难** | **等 20 分钟后失败/被取消 ⇒ 0 产出。** 取消会丢弃全部已生成章节（`app.py:713-727` + `preactor.py:482-485`），且没有任何重试机制。 |
| **单次默认运行成本** | 约 **68 万 token**（Claude Sonnet 口径约 **¥28 / $3.9**），墙钟 **10～22 分钟**，API 调用 **≈ 381 次**。 |

### 1.2 JTBD 拆解（Jobs To Be Done）

**Functional（要完成的任务）**

1. 当我卡文时，我要有人给我**几个不同的、都能往下走的走向**，让我挑一个 —— 而不是我从 500 个 AI 段落里盲选。
2. 当我写完一章时，我要**能改这一章**（重写、续写、改设定），而不是整本重跑。
3. 当我连续写 30 天时，我要 AI **记得我的人物设定和伏笔**，并且不违反。
4. 当我交稿时，我要**符合平台规范**（章节字数、章节标题格式、分卷）。

**Emotional（要的情绪）**

5. 我要**掌控感**——改一个字能立刻看到结果，而不是等 20 分钟换来一个我不想要的开局。
6. 我要**不焦虑**——中途失败不意味着前功尽弃。
7. 我要**不内疚**——产出的东西是我自己的，不是「AI 味」的量产稿。

**Social（要的身份认同）**

8. 我要它**辅助我**而不是**替我写**；我是一个作者，不是一个操作员。

## 2. 现状用户旅程（逐屏走查）

### 2.0 旅程全景（当前真实路径）

```
[启动] python -m novel_preactor --web  →  http://localhost:8000
   ↓  （无注册/无登录/无项目列表/无历史/无引导教程）
[屏1] 配置页 /            —— 一次性填 30+ 字段，11 个参数卡
   ↓  点击「🚀 开始生成小说」→ POST /api/start
[屏2] 进度页 /progress/{id}  —— 干等 10~22 分钟，只有进度条 + 原始日志
   ↓  SSE: result_ready → 1.5s 后跳转
[屏3] 结果页 /result/{id}  —— 书名 + 分数表 + 只读预览 + 4 个下载按钮
   ↓  （到此为止：没有任何修改、续写、重跑、对比、分享的出口）
[屏4] 文件夹 output/{run_id}/  —— MD / params.yaml / eval.json（用户自己翻目录）
```

## 4. 价值主张评估

### 4.1 主张复述

> 「对同一个故事前提并行预演 1~500 条情节线 → 四维打分择优 → 产出整本小说」（README:50）

### 4.2 「并行预演 500 条情节线」在代码里站不住的三条硬证据

1. **分支选项从未被消费。** 导演 prompt 明确要求输出 `branch_choice` 与 `branch_options`（`prompts.py:134-137`），但全仓库 `grep branch_choice` 只命中 prompt 定义与 `agents.py:791` 的解析失败兜底。**没有任何编排逻辑把不同版本钉在不同分支上。** 版本之间的差异 100% 来自 LLM 采样随机性。
2. **每个版本自己挑大纲，3 个版本大概率挑同一份。** `preactor.py:128-181`：每个版本独立生成 3 份角度大纲、独立评估、独立选「最优」。3 个版本面对同样的 3 个角度和同样的 prompt，评估器又偏好同一个「因果链清晰」的解 ⇒ **3 倍 token 换取 3 条同质线**。
3. **结局也被强制收敛。** `preactor.py:118-126`：自动结局写回共享的 `config.story_end`，先到先得 ⇒ 后续版本不再生成自己的结局。**「探索不同结局」在代码上不存在。**

> 附带：500 版本意味着 500 × 20 章 × 6 次调用 ≈ **6 万次 API 调用、1 亿+ token**、500 并发协程必撞限流。`preactor.py:681-685` 只在日志里 warn 一句，UI 层面完全没有护栏。

### 4.3 「四维择优」的判别力问题

- 评估者是**生成者同源、同一个 LLM**（`agents.py:962-1018`），自评存在明显偏袒；四维分数是 0-10 的连续值，但 UI 把它渲染成 `score-bar` 像素条（`result.html:102`），**掩盖了「3.2 vs 3.4」其实是噪声**。
- `evaluator.py:91` 认为分数差 <5% 就算「接近」——这恰恰说明**分数本身区分度不足**，而 Web 模式直接跳过人工裁决（`app.py:168`）。
- 更根本的问题：**四维分数不是网文作者的评价维度**。网文作者关心的是「前三章留不留人」「爽点密度」「会不会崩人设」「能不能日更」。

### 4.4 与「先出大纲 → 人改 → 逐章写 → 局部重写」工作流的对比

| 维度 | 选墨集（当前） | 人机共写工作流（目标） |
|---|---|---|
| 首次可用产出 | 10～22 分钟后一次性拿到 8 千字不可改文本 | 90 秒后拿到 3 个大纲 + 1 章草稿，可立刻改 |
| 单次 Token 消耗 | ≈68 万（3 版本） | 首轮 ≈6 万；后续按需增量（重写一章 ≈8 千） |
| 纠错成本 | 错一行 ⇒ 重跑全程（20 分钟 + 全额花费） | 改一行 ⇒ 重写 1 章（30 秒） |
| 人的角色 | 消费者 | 决策者 + 消费者 |
| 可持续性 | 一次性（读完就没了） | 可日更（每天一个 session） |
| 平台适配 | 无 | 分章/分卷/字数/标签 |
| 与「网文作者」的真实匹配 | 低 | 高 |
| 与「内容工作室批量出稿」的匹配 | **高** | 中 |

**结论：当前形态与「网文作者」的真实工作流性价比极差；与「批量出短篇稿」的工作流高度匹配。**

### 4.5 明确立场：保留 / 改造 / 推翻

**推翻（3 项）**

1. **推翻「自动择优 → 唯一赢家」的终局模型。** 择优应该是**给人看的选择题**，不是给 AI 的独断权。改造：Web 端恢复并强化人工择版（`evaluator.py:93-113` 已有 CLI 实现），结果页并排展示 3 条线 + 各自大纲/首章/梗概，用户拍板。
2. **推翻「一次运行 = 一整本书」的产品单元。** 改造为「一次运行 = 一段可编辑的稿子」，并把「多版本并行」降级为**章节级头脑风暴**（一次 3 个走向，成本降到 1/10）。
3. **推翻「无状态的一次性执行」。** 引入运行持久化、断点续跑、章节 checkpoint、取消保留。

**改造（5 项）**

4. **「多走向」从后台走向前台。** 让 `branch_options`（`prompts.py:134-137`）真正生效，并渲染成可点击卡片。这是整个产品唯一真正稀缺的差异化能力。
5. **大纲/设定/人物从「AI 内部产物」变成「用户资产」。** 目前大纲存在于 `state.outline` 却从未展示；应在结果页可见、可编辑、可锁定。
6. **四维打分降级为「体检报告」，不作为选型依据。** 增加网文真正关心的维度：开篇钩子、爽点密度、角色一致性、节奏、字数达标率。
7. **成本与时长必须在运行前可见。** 这是付费产品的底线。
8. **导出格式与文档必须一致**（MOBI/AZW3），且增加「可编辑工程包」。

**保留（6 项，做得好，别动）**

9. 多 Agent 角色分工（导演/主角/NPC/写手）—— 结构合理，是质量的基础。
10. RAG 故事记忆（`story_memory.py`）—— 是「长文连贯」的关键资产，只需产品化为「设定集 + 伏笔面板」。
11. 三幕剧节奏控制与动态压力（`agents.py` `_calc_pacing`）—— 思路对，需加「爽点」维度。
12. 183 位作家风格库 + 公版/在世标注 + 风险提示（`index.html:332-348`）—— **合规意识是本项目的加分项**，中文网文圈几乎没有同类产品做这个。
13. 起名引擎（`naming.py` 规则 + LLM 择优）—— 效果不错，只是摘要没接上。
14. 多格式导出与前附文（目录/引言/楔子/人物表）—— 交付完整度好。
15. 13 家 API 供应商 + 国内模型优先 —— 契合国内网文作者。

### 4.6 一个被忽视的战略性事实

**它做不了「长篇」。** 章节上限 30（`index.html:78` 允许到 100，但 `preactor.py:202` 用 `effective_max_chapters`；且每章字数天花板 1,500 字，`preactor.py:552`）⇒ 理论上限 4.5 万字，30 章 × 1,500 = 4.5 万字。而中文网文是 20 万～200 万字。**当前架构下，目标字数填 30 万会被静默截断到 15%，界面毫无提示。** 这不是调参能解决的，是「一次性生成」范式本身的容量上限。

## 5. Web UI 专项评估

### 5.1 信息架构

当前 IA 只有三页一纵到底：**配置 → 进度 → 结果**。缺三个关键节点：

- **项目/作品库**（多部作品管理、续写入口、历史）
- **作品工作台**（章节列表、设定集、大纲、伏笔、版本）
- **对比/选择页**（在多版本之间做决策的地方，目前被压缩进结果页的一个表格）

严重度：**高**。当前 IA 决定了「跑完即终点」，产品的全部价值被压在第一屏。

### 5.2 字段数量

配置页共 **11 张卡片、约 30 个可见字段**（`index.html:16-216`），其中：
- 真正决定结果的只有 **4 个**：主角设定、世界观、开头、风格。
- **7 个是内部旋钮**（章节上限、NPC 上限、Token 预算、质量模式、主角团模式、NPC 策略、NPC 名字风格），用户没有判断依据。
- **3 个是元操作**（前附文 4 个勾选、书名风格、自定义风格）。

**结论：对新手是灾难。** 但解法不是删字段（它们对高级用户有价值），而是**分层 + 默认值可见 + 预估联动**：

```
第一步（必填，4 项）  →  一句话创意 + 题材模板 + 主角 + 风格
第二步（自动生成，可改）→ 世界观 / 开头 / 结局 / 人物表  ← AI 补全，用户只改不要的
第三步（折叠，高级）   → 11 个参数全部折叠，附「这些参数会怎么影响结果」的说明
```

### 5.3 进度页信息设计

| 维度 | 现状 | 问题 | 建议 |
|---|---|---|---|
| 进度 | 单条 5%→55%→100% 的条 | 无法表达「3 个版本各自到第几章」 | 每版本一条独立进度条 + 章节数/字数/剩余估计 |
| 反馈 | 版本卡片在最后一刻才出现 | 20 分钟零反馈 | 每章推送 `chapter` 事件，实时更新卡片 |
| 预期 | 无 ETA、无已用时、无剩余 | 等待焦虑 | 顶部固定「已用 6 分 12 秒 · 预计还需 4～7 分钟」 |
| 可控 | 只有「取消」 | 取消=全丢 | 加「仅停止剩余版本，保留当前进度」 |
| 成本 | 无 | 无法判断是否该继续 | 实时显示「已消耗 ¥12.4 / 预算 ¥28」 |
| 日志 | 原始 logger 全量倾泻 | 噪音 + 术语 + 跨 run 串 | 折叠为「技术日志」，默认展示人话进度 |
| 安全感 | 无 | 怕刷新/怕断线 | 明确「后台运行中，可离开此页」+ 运行历史入口 |

### 5.4 结果页可用性

**做得好的**：书名与候选书名的视觉呈现（`result.html:17-43`）、统计面板（46-64）、版本对比表（67-147）、两个 Tab 分区、下载区。

**问题**：

1. **只读**——没有任何编辑入口（最致命）。
2. **情节摘要永远为空**（`naming.py:524-529`）⇒ `result.html:22-26` 是死代码块。
3. **非获胜版本不可读**（`result.html:138` 只有 MD 下载）⇒ 用户付了 3 倍钱却看不到另外 2 倍产出。
4. **预览 ≠ 下载**（`app.py:756-768` 每次 GET 重新生成前附文）。
5. **10 列表格 + 像素条**（`result.html:72-146`）信息密度高但决策价值低。
6. **字数不与目标对比**（`result.html:60-63`）。
7. **无章节导航、无搜索、无字号调节**（`style.css:286-295` 固定 `70vh` 内滚动）。
8. **`| safe` 注入**（`result.html:157`）未转义。

### 5.5 错误提示与空状态

| 场景 | 现状 | 评价 |
|---|---|---|
| 启动时缺 API Key | `app.py:572-580` 400 + 明确说明检查了哪些环境变量 | ✅ 好 |
| 表单校验失败 | `app.py:616-618` 拼接错误信息，JS 显示在 `#form-error` | ⚠️ 可用，但未定位到具体字段 |
| 运行中 API 报错 | 只在日志里；结果页 `title` 属性藏 `termination_reason` | ❌ 用户看不到 |
| 全部版本失败 | 结果页显示 novel 为「# 错误：没有可用的版本」（`writer.py:115`） | ❌ 把错误当成作品交付 |

| 运行不存在 | 404 HTML（`app.py:636`、`:733`、`:751`） | ❌ 非 JSON、无引导 |

**建议**：建立统一错误模型 `{code, message, action_hint, retryable}`，前端按 code 渲染；所有失败路径必须有**「发生了什么 / 你可以做什么」**两段式文案。

### 5.6 移动端适配

- 断点只有 900px / 480px（`style.css:411-438`）。
- 配置页 6 列栅格在 901～1200px 区间挤压。
- 结果页 10 列表格在手机上**必然横向溢出**且无滚动容器。
- 预览区 `max-height:70vh` 内滚动 + 无目录，手机上读长文体验差。
- 进度页日志流 `max-height:300px`（`style.css:367`）在手机上占满屏。

**结论：移动端只能「看进度」，不能「用产品」。** 而网文作者大量在手机上构思和改稿——这是重要场景。

### 5.7 暗色主题与可读性

- 配色变量体系完整（`style.css:3-30`），`#0d1117` 底 + `#e6edf3` 正文，对比度充足。
- `--text-secondary:#8b949e` / `--text-muted:#6e7681` 在 `--bg-card:#1c2128` 上约 4.5:1，尚可，但正文里大量使用 muted（页脚、小字）偏灰。
- **正文阅读区没有为长时间阅读优化**：`line-height:1.8`、字号 0.95rem 尚可，但没有「宋体/思源宋体」等中文正文字体栈，中文衬线体缺失，长文阅读体验一般。
- 无浅色模式、无字号缩放、无高对比度模式。
- 暗色 + 长时间阅读的「写作工具」场景不占优（多数写作工具默认浅色或提供双主题）。

### 5.8 国际化

- 界面 100% 硬编码中文，无 i18n 层、无语言切换、`lang="zh-CN"` 固定。
- 写作风格库含日/英/俄作家 55 位，但界面无英文版。
- **判断**：若定位是「中文网文工具」，全中文是**优点**（一致性）；若想出海需重做。**建议明确选择「中文优先」，并把 i18n 列为 Won't have（本期）**，避免两头不到岸。

### 6.5 「免费用户能跑几次」

以「注册送免费额度」为口径：

| 免费额度方案 | 能跑几次（默认 3 版本 / 8 千字） | 体验后果 |
|---|---:|---|
| 20 万 token（Claude 口径） | **0 次** | 在第 11 章左右触发「总 token 预算不足」（`preactor.py:209-213`），**钱烧了、书没出来** |
| 50 万 token | 0.7 次 | 跑到第 15 章断掉，评分为空 |
| 100 万 token | 1.5 次 | 勉强 1 次成功，用户会认为「运气好才成功」 |
| ¥5 额度（DeepSeek/国产） | **≈ 2 次** | 可接受 |
| 「1 次免费生成」定性赠送 | 1 次 | 但失败/超时/取消概率不低 ⇒ **期望拿到成稿 < 1 次** |

**结论：以 68 万 token / 每次的消耗，免费额度必须给到 **100 万 token 以上**（或走国产模型路线给 ¥10+），否则「免费试用」必然是负体验。** 更糟的是：**没有任何机制让用户在烧钱前知道要烧 68 万 token。**

### 6.6 降本机制建议（按性价比排序）

| 优先级 | 措施 | 节省 | 实现成本 |
|---|---|---:|---|
| P0 | **大纲提升到 orchestrator 层，只生成一次**（现每版本各生成 3 份） | 省 2/3 大纲开销 ≈ 2.2 万 token/次（3%） | 低（改 `preactor.py:128-181`） |
| P0 | **预算改用真实 API `usage` 计量**（现低估 3 倍） | 不省，但消除超支 | 低（`preactor.py:451`） |
| P0 | **前附文落盘缓存**（现每次刷新/下载都重跑） | 省重复调用 2,100 token × N | 极低 |
| P1 | **评估只喂摘要而非全文** | 评估输入 3.6 万 → 0.5 万（省 3.1 万，5%） | 中（`agents.py:962-1018`） |
| P1 | **角色分离模型**：导演/主角/NPC 用便宜模型（Flash/国产），仅写手用好模型 | 输入 token 大头在导演/主角（3,800/7,800 ≈ 49%），用 1/5 价模型 ⇒ **总成本降约 35～45%** | 中（`LLMClient` 按角色分实例） |
| P1 | **RAG 记忆抽取降频到每 3 章一次** | 省 13% 调用 ≈ 8.4 万 token（12%） | 低 |
| P1 | **N=1 先行 + 合格才扩展**：先跑 1 版，检查达标再补 2 版 | 平均省 40～50% | 中（编排改造） |
| P2 | **Prompt 瘦身**：导演 prompt 含上章全文；改用 RAG 摘要 | 导演输入降 30% ⇒ 全局省 8% | 中 |
| P2 | **章节级 checkpoint + 断点续跑** | 不省，但避免**重跑浪费**（失败一次的浪费常常超过一次完整运行） | 中高 |
| P2 | **`num_versions` 硬上限 10 + 运行前金额预估** | 避免 500 版本的账单灾难 | 低 |
| P2 | **小模型做「合格性预检」**：先用 8K 小模型跑 3 章，不合格直接终止 | 省掉「跑满 20 章才发现跑偏」 | 中高 |

**综合乐观估计：上述 P0+P1 全部落地后，一次默认运行可压到 ≈ 30～35 万 token / ¥12～15（Claude 口径）或 ≈ ¥1.2（国产模型），墙钟 8～12 分钟。**

## 7. 定位与差异化

### 7.1 它现在是什么

> **一个自托管的多 Agent 短篇批量生成器**：输入设定 → 并行跑 3 条 AI 剧情线 → LLM 自评挑一条 → 输出 8 千～3 万字成品 + 4 种格式文件。
> 技术上做得不错、文档齐全、审美在线、但**没有任何"创作"环节**。

### 7.2 它应该是什么

> **一个面向中文网文作者的「情节决策 + 章节工作台」**：把 AI 的并行想象从后台搬到前台让人选择（3 个走向），把 AI 产出从"成品"降级为"草稿"，把「设定集 / 伏笔 / 字数 / 平台规范」做成可积累的创作资产。
> 核心指标从「一次生成了多少字」变为「作者在其中写了/改了多少字」。

### 7.3 三个候选定位方案

#### 方案 A：**网文情节决策台（Plot Decision Desk）**

| 项 | 内容 |
|---|---|
| **用户** | 已有稳定日更能力的网文作者（番茄/起点签约或准签约） |
| **场景** | 卡文时、每天开工时、章节规划时 |
| **核心功能** | ① 输入前提 → 输出 3 个**可点选**的走向卡片（含大纲、冲突点、爽点预告）② 选定后展开 5～8 章「章节走向树」③ 每个走向可续写/回溯改写 ④ 设定集与伏笔面板 ⑤ 导出到番茄/起点模板 ⑥ 单次成本压到 ¥1 以内 |
| **取舍** | ✅ 成本低、见效快、贴合卡文这个真痛点  ⚠️ 放弃「一键出整本」的完整叙事  ⚠️ 放弃工作室批量场景  ⚠️ 需要把现有多版本并行改造成「走向选择 + 局部展开」，工程量中等 |
| **差异化** | 「不替你写，帮你选」——中文圈几乎没有认真做**情节决策**而非**文字生成**的工具 |
| **商业化** | 订阅制（¥30～50/月），按走向包计费 |

#### 方案 B：**短篇/中篇批量成书工厂（Short-Story Factory）**

| 项 | 内容 |
|---|---|
| **用户** | 内容工作室、公众号/知乎故事号、小说推文号运营者、AI 聚合内容农场 |
| **场景** | 每天产出 10～50 篇不同题材不同风格的故事 |
| **核心功能** | ① 题材模板库（都市脑洞/悬疑反转/古风虐恋…）② 批量队列：一次投 50 个设定，自动排队跑 ③ 多版本并排预览 + 一键择优 ④ 格式合规导出（公众号/知乎/短故事平台）⑤ 去 AI 味后处理（句式扰动/禁用词）⑥ 用量与成本看板 |
| **取舍** | ✅ **与当前代码形态最贴合，改造成本最低**  ⚠️ 放弃「长篇网文」与「作者工具」叙事  ⚠️ 内容质量要求低，护城河薄  ⚠️ 法律与平台合规风险更高 |
| **差异化** | 「工程化 + 成本可控 + 合规导出」，而非「AI 会写小说」 |
| **商业化** | 按量计费 + 团队席位 |

#### 方案 C：**AI 副驾工作台（Copilot Desk）**

| 项 | 内容 |
|---|---|
| **用户** | 有一定写作基础、想用 AI 提效但拒绝「被代笔」的作者（人数最多、最难服务） |
| **场景** | 每天写 4,000 字：查设定、顺句子、扩写场景、接续下一章 |
| **核心功能** | ① 作品工作台：章节树 / 设定集 / 人物卡 / 伏笔时间线 ② 逐章 AI 操作：重写、扩写、缩写、换视角、接续 ③ 多轮对话改稿 + 版本 diff ④ 角色一致性 & 伏笔回收检查 ⑤ 平台字数与格式规范 ⑥ 局部「多走向头脑风暴」（把现在的并行预演降级为单章工具） |
| **取舍** | ✅ 长期留存与付费意愿最高  ⚠️ 工程量最大（≈6～12 个月）  ⚠️ 需要重写大部分 Web UI  ⚠️ 现有「一次性生成」内核要拆成「可组合的写作算子」  ⚠️ 与竞品（秘塔 AI 写作、讯飞绘文、各家网文 AI 助手）正面竞争 |
| **差异化** | 「设定集 + 伏笔 + 一致性」这套中文网文特有的工程化能力 |
| **商业化** | 订阅制（¥68～128/月）+ 按量超额 |

### 7.4 方案对比

| 维度 | A 情节决策台 | B 成书工厂 | C 副驾工作台 |
|---|---|---|---|
| 与现有代码契合度 | 中（需改预演为选择） | **高**（几乎不用改核心） | 低（需重构） |
| 目标用户规模 | 中 | 小 | **大** |
| 用户付费意愿 | 中高 | 中 | **高** |
| 留存（复购/日活） | 中 | 低（任务型） | **高** |
| 竞争壁垒 | 低 | 低 | **中高**（设定集+伏笔） |
| 合规/法律风险 | 低 | 中高 | 低 |
| 上线时间 | 1～2 个月 | 2～4 周 | 6～12 个月 |
| 收入天花板 | 中 | 低 | **高** |
| 是否解决「卡文」这个真痛点 | **是** | 否 | 部分 |

### 7.5 推荐路径

**主线选 C（副驾工作台），但按 A → B → C 推进，且 A 的能力内核是 C 的一个模块。**

- **第一步（0～2 个月，P0）做「A 的最小版」**：把「并行预演」从后台搬到前台——在结果页以可点选卡片呈现 3 条走向（含各自大纲与首章），让人选；补上成本预估、真实计量、断点续跑、取消保留、历史记录。**这一步不重写引擎，改动集中在 `webui/` 与编排层，却能立刻兑现产品最核心的差异化。**
- **第二步（2～4 个月）做「B 的付费版」**：批量队列 + 模板库 + 成本看板 + 合规导出，服务工作室付费，**先收钱验证付费意愿**。
- **第三步（4～12 个月）做「C」**：章节工作台、设定集、伏笔面板、逐章改稿、平台适配。**A 与 B 的产出（走向数据、模板、用户反馈）正是 C 的数据资产。**

**明确不要做的**：不要继续加「版本数上限」「更多作家风格」「更多导出格式」这类**加法**——它们都不改变「一次性交付」的范式天花板。

### 路线图上的取舍纪律
